# Deploying the backend to Cloudflare Workers (`trading-backend`)

The API is a single Express app (`src/app.ts`) that runs in **two** places:

| Environment | Entry point | How it runs |
| --- | --- | --- |
| Local dev (Docker Postgres) | `src/server.ts` | `npm run dev` → `app.listen()` |
| Production (Cloudflare Workers) | `src/index.ts` | `http.createServer(app)` + `httpServerHandler` from `cloudflare:node` |

Both entry points share the same Express app and the same Prisma client
(`src/lib/prisma.ts`), which uses the **node-postgres driver adapter**
(`@prisma/adapter-pg`). On Workers, `pg` connects over TCP via Cloudflare's
built-in `cloudflare:sockets` (`nodejs_compat`).

## Why the extra plumbing exists

1. **`cloudflare:node` / `node:http`** — Workers can run a Node.js HTTP server
   only with the `nodejs_compat` flag **and** the `enable_nodejs_http_server_modules`
   flag (auto-enabled for compatibility dates ≥ `2025-09-01`). Both are set in
   `wrangler.toml`.
2. **`src/lib/bodyParser.ts`** — replaces `express.json()` / `express.raw()`.
   Importing Express causes it to read `bodyParser.json`, which pulls in
   body-parser → raw-body → **iconv-lite**, and iconv-lite crashes on the Workers
   runtime (`require_streams(...) is not a function`) because it eagerly loads a
   Node `streams` helper.
3. **`src/shims/body-parser.ts` + `[alias]` in `wrangler.toml`** — Express still
   imports `/ reads from` `body-parser` at load time, so the Wrangler build aliases
   the package to a no-op shim. Node/local development is unaffected.

4. **`src/middleware/prismaScope.ts`** — gives every request its **own** Prisma
   client (and therefore its own `pg` pool). Cloudflare's TCP socket docs are
   explicit: *"TCP sockets cannot be created in global scope and shared across
   requests. You should always create TCP sockets within a handler."* A
   module-level pool hands request A's socket to request B; the runtime refuses
   that I/O, the awaiting promise never settles, and the edge cancels the
   request with *"your Worker's code had hung and would never generate a
   response"*. That response is generated by the edge, so it carries **no CORS
   headers** — which the browser reports as *"blocked by CORS policy: No
   'Access-Control-Allow-Origin' header is present"*. The middleware opens an
   `AsyncLocalStorage` scope per request; the `prisma` proxy in
   `src/lib/prisma.ts` resolves to that request's client (created lazily, so
   `/api/health` and preflights pay nothing) and the pool is closed on
   `res.finish` / `res.close`. Route files need no changes. See **Troubleshooting**.

## One-time secret setup

Secrets are **not** in `wrangler.toml` (only `[vars]` are). Set them once:

```bash
cd backend
npx wrangler secret put DATABASE_URL       # Neon pooled connection string
npx wrangler secret put JWT_SECRET
npx wrangler secret put JWT_REFRESH_SECRET
npx wrangler secret put RESEND_API_KEY
npx wrangler secret put STRIPE_SECRET_KEY
npx wrangler secret put STRIPE_WEBHOOK_SECRET
```

`DATABASE_URL` should use the **pooled** Neon endpoint (`...-pooler...`) and must
**not** include `channel_binding=require` (the code strips it, but leave it out).

## Build / test / deploy

```bash
cd backend

npm run build            # local Node build (tsc) — not required for Workers
npm run deploy:dry-run   # verify the Worker bundles without deploying
npm run dev:worker       # run the Worker locally (wrangler dev)
npm run deploy           # publish to the trading-backend Worker
```

Or do secrets + deploy + smoke tests in one step:

```powershell
cd backend
.\deploy-worker.ps1
```

`wrangler deploy` prints the live URL, which is
`https://trading-backend.<your-workers-subdomain>.workers.dev`. Wrangler bundles
`src/index.ts` directly (TypeScript included), so there is no separate build step
for the Worker. `--dry-run` above verifies the bundle without deploying.

Wrangler must be authenticated before deploying (`npx wrangler login`, one browser
click). Note: an older Wrangler stored its session under
`%APPDATA%\xdg.config\.wrangler\`, while current Wrangler looks in
`%USERPROFILE%\.wrangler\`. If `wrangler whoami` says "not authenticated" even
though you logged in before, that stale session is the reason — just log in again.

## Frontend

`frontend/src/config/api.ts` builds the base URL as `${VITE_API_URL}/api`, so
`VITE_API_URL` must be the Worker **origin only** (no `/api` suffix). Cloudflare
Pages inlines env vars at build time, so set it and **redeploy** the Pages project
(Settings → Environment Variables → Production → `VITE_API_URL`).

```
VITE_API_URL=https://trading-backend.<your-workers-subdomain>.workers.dev
```

`FRONTEND_URL` is already set in `[vars]` above, and the CORS middleware in
`src/app.ts` also hardcodes `https://trading-journal-dlb.pages.dev`, so no CORS
change is needed for the Pages origin.

## Verifying a deploy

Replace `<WORKER_URL>` with the URL printed by `wrangler deploy`:

```bash
curl.exe -i https://<WORKER_URL>/api/health
# 200 {"status":"OK","message":"Trading Journal API is running","version":"4.0.0","platform":"cloudflare-workers"}

curl.exe -i -X OPTIONS https://<WORKER_URL>/api/auth/login \
  -H "Origin: https://trading-journal-dlb.pages.dev" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"
# 204 with Access-Control-Allow-Origin: https://trading-journal-dlb.pages.dev
```

If you instead see `x-render-routing: no-server` or a bare 404 with no
`Access-Control-*` headers, the old Render host is still being used somewhere —
check the Pages `VITE_API_URL`.

## Troubleshooting

### "blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present"

This is almost always **not** a CORS configuration problem. Rule it out first:

```powershell
# Preflight for the exact route the browser complains about
curl.exe -i -X OPTIONS 'https://<WORKER_URL>/api/trades?page=1&limit=20' `
  -H 'Origin: https://trading-journal-dlb.pages.dev' `
  -H 'Access-Control-Request-Method: GET' `
  -H 'Access-Control-Request-Headers: authorization'
# 204 + Access-Control-Allow-Origin / Allow-Headers: authorization  => CORS is fine

# Same route without a token (never reaches the database)
curl.exe -i 'https://<WORKER_URL>/api/trades?page=1&limit=20' `
  -H 'Origin: https://trading-journal-dlb.pages.dev'
# 401 WITH Access-Control-Allow-Origin  => the response path is fine
```

If both of those return `Access-Control-Allow-Origin` but the browser still
fails, the request is dying **inside the handler** and the edge is replacing the
response (no CORS headers). Watch it live:

```powershell
cd backend
npx wrangler tail trading-backend --format json   # then reproduce in the browser
```

Look for `"outcome"`, `"exceptions"`, `"logs"` and `"status"` in the tailed
events. Two failure modes seen in this project:

| Tail shows | Meaning | Fix |
| --- | --- | --- |
| `"outcome": "exception"` + `Worker's code had hung and would never generate a response` | A `pg` connection from a previous request was reused (see plumbing note 4). | Ensure `app.use(prismaScope)` is registered **before** every DB-touching route and that nothing caches a `PrismaClient` in module scope. |
| `Raw query failed. Code: WASM_ERROR. Message: Error: missing field 'fields'` on `create`/`update` | The deployed Worker bundle is **stale**: its Prisma client/query-compiler WASM no longer matches the installed `@prisma/client` (`wrangler deploy` re-uploads it). | Re-run `npx wrangler deploy`. If it persists, delete `node_modules/.prisma` + `node_modules/@prisma/client`, `npx prisma generate`, redeploy. |

### A single request hangs for ~30–100 s, then fails

Same root cause as above: locally `wrangler dev` reports
*"The Workers runtime canceled this request because it detected that your
Worker's code had hung and would never generate a response."* (the browser sees
`net::ERR_FAILED` + a CORS error instead). Requests that deadlock and requests
that succeed look random because it depends on whether the pool still holds an
idle socket from a previous request.

Fast local reproduction (per-request scoping disabled) was:
`/api/trades/stats` and `/api/subscriptions/status` — both deadlocked
reliably, because `/api/trades/stats` fans out with `Promise.all` and the
dashboard fires several authenticated calls at once. After the fix, every one
of them returns `200`, sequentially **and** concurrently.
